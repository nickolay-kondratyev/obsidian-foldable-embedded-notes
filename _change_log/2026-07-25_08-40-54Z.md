An embed that never resolves (`![[typo]]`) kept its readiness MutationObserver
forever: the observer only disconnected when a title appeared or a mutation
revealed a media class, and an unresolved embed renders as
`internal-embed is-loaded file-embed mod-empty` — neither. MEASURED before the
fix: two unresolved embeds re-rendered three times grew live observers
2 -> 4 -> 6, each retaining a detached section subtree.

FIX: the wait is now a `MarkdownRenderChild` (`src/pendingEmbedObserver.ts`), so
the observer dies with the embed span rather than with the plugin. A per-instance
WeakSet guard stops one span from holding two observers when Obsidian REUSES
rendered DOM (Live Preview widgets). `teardown()` still unloads observers
explicitly — MEASURED: plugin-disable does NOT unload `ctx.addChild` children
whose DOM Obsidian keeps.

REJECTED, and the ticket's own design was wrong here: bailing early on
`file-embed` to avoid creating the observer at all. MEASURED on 1.12.7 — when
the missing note is later CREATED, Obsidian upgrades the SAME span in place to
`markdown-embed`, so that bail would silently leave the embed unfoldable. The
render-child binding alone bounds the leak, so the classification change was
unnecessary as well as lossy. `mod-empty` is likewise not terminal.

Tests: two new e2e specs, both RED-for-the-right-reason before their fix — an
observer-growth spec (`Received: 6`) and a late-created-target spec
(`Received: 0`). Full suite 57 passed / 0 failed.
