The reveal set was built from `range.head` only, so a selection spanning the marked line (or select-all) hid the dash even though Obsidian keeps revealing its own raw `![[x]]` under a selection. Net effect: the line displayed `![[x]]` while the file held `![[x]]-`, with the invisible dash sitting inside the range the user was about to type over.

The reveal is now a per-line overlap test against the selection — `range.from <= line.to && range.to >= line.from` — rather than a lookup of the line under the head. Direction-independent (`from`/`to`, not `anchor`/`head`), correct for multi-range and rectangular selections, and a bare cursor is the degenerate empty-range case, so the pre-existing cursor-on-line reveal survives with no special branch. Deliberately no Set of touched line numbers: that would be O(lines-in-selection) per decoration rebuild on every selection change.

e2e: two tests select from the line ABOVE to the line BELOW the marked line, so neither endpoint sits on it and head-only logic cannot pass them; one forward, one backwards. The backwards test asserts the head really precedes the anchor, which establishes that Obsidian's `setSelection` does not normalise direction. Required exposing `setSelection`/`getCursor` on the e2e Obsidian facade.
