`stripFoldMarker` (`src/foldableEmbedsPostProcessor.ts`) treated an empty remainder after the dash as "end of line", but it only meant "end of THIS text node". Inline markup right after the dash renders as a SIBLING element, so the dash sat alone in its own node: `![[x]]-**bold**` and ``![[x]]-`code` `` silently folded AND lost the user's literal dash, while the plain `![[x]]-x` correctly stayed literal.

Now the marker arms only when the dash is followed by whitespace or a REAL end of line — new private `isEndOfLine`: nothing follows the node in its parent, or a `<br>` does. Uses obsidian's `Node.instanceOf` rather than `instanceof` so a popout window's `<br>` (different realm) is still recognised. Structural check, no regex lookbehind, keeping mobile/iOS Safari support.

e2e (`e2e/foldable-embeds.e2e.ts`): `![[child]]-**bold**` negative case (written failing first, confirmed failing for the right reason), `![[child]]- tail` guarding the restructured whitespace branch, and a `marker-soft-break.md` fixture for the `<br>` branch — mutation-proved coupled to it. lint / build / full e2e green (46 passed), independently re-run by the reviewer.

Live Preview is unaffected: `src/livePreview/markedEmbedLines.ts` matches whole RAW text lines, so this DOM-shape bug class cannot occur there.

- nid_3axo1iklky5s5n9us7947nr4i_e — `**![[x]]-** tail` (embed wrapped in inline markup) still loses its dash; needs an ancestor walk.
- nid_sos38zx0quvy2ec2j5seqsh7e_e — reading mode folds `![[x]]- tail`, Live Preview does not; a product decision, not a bug fix.
